# Acorde — release gates and implementation priorities

**Status:** testing-only product build. Do not merge this branch to main or promote publicly without owner review. Canonical backend: [Acorde Lab](https://github.com/dokarpov/intake-integrity-lab). Marketing, demo and commercial calculators: this repository. One operator inbox; no parallel CRM or "demo as production" claims.

## Product promise and boundaries

Acorde helps teams accept sales enquiries without confidently linking them to the wrong customer. It routes ambiguous identity matches to a reviewer, preserves consent/source evidence, and aims for a durable, idempotent delivery path to configured CRM/1C. Deduplication is **not** equivalent to verified identity; matching alone must never auto-merge people or edit their records.

The customer-facing estimate uses **three prefilled sliders** (staff, records per staff member/day and share requiring review), each with a **fine initial scale and a visible “More range” button**. These are slider *scales*, not arbitrary limits on company size. Their ultimate validated ranges are staff 1–10,000, records 1–10,000/day, review rate 0–100%, and tool fee €0–€1,000,000/month; all values recalculate without typing. Choosing “We use a tool” reveals its fee slider **immediately below the choice, before the staff slider**, with a local message stating exactly how the fee changes cost; the review rate remains user-selected. Switching back to manual keeps the tool fee selection but excludes it from current costs. The result shows only (1) current review hours, (2) potential hours freed at a 50% illustrative reduction, (3) value of that time, and (4) a compact current staff + software cost breakdown. A single brief disclosure contains the assumptions (20 workdays, 10 minutes per case, €28 per staff hour). This is a scenario, not realized cash savings. The annual panel, 30–70% range, long formula commentary and progress bar were removed from the visible calculator.

For email: the calculator now has a **Tally-free direct-mail transport** implemented as Google Apps Script, with server-side recalculation, bounded send quotas, a fixed no-spam report, and separately confirmed optional consent. [Owner activation and test instructions](GOOGLE_MAIL_SENDER.md). The mail sender executes under the owner's Google account, **but still requires the owner to authorize/deploy Apps Script and configure `mailer-config.mjs`**. Until activation, the automatic sending action stays disabled and copy-only; never claim actual delivery. Automated newsletters are not implemented; only a private confirmed opt-in ledger is designed. Tally is no longer involved in report sending or subscription; existing paid-audit enquiry service remains separate and unchanged. The user-facing form displays the **optional unchecked newsletter checkbox directly ABOVE Send**. It appears disabled when the owner-authorized sender is unavailable; a report request alone never subscribes someone. The email is now short: estimate, proposed deduplication API workflow and simple CRM/source reply. No five-record or multi-day diagnostic task. [API-first CRM-native integration contract](API_FIRST_CRM_INTEGRATION.md) documents the proposed one-source/one-CRM pilot and its separate provider verification gate. No live connector claims.

## Customer-facing UX rule — 11 November 2026

User-validated rule: **If the element is not needed to understand the decision or complete the next action, remove it.** Small text, repeated explanations, ornamental headers and inactive controls are not useful conversion content. Primary business actions must be unmistakably more prominent than supporting actions.

For the calculator: user selects current process + three sliders → sees relevant figures → full-width **Request a paid audit** button immediately beneath results. Secondary **Copy estimate** is available; calculation assumptions open only on request. Once owner-authorized sending is live, enable an optional email form below the primary action with newsletter opt-in visibly unchecked. **Do not display unusable email controls or descriptions of internal infrastructure** before integration. Keep legal privacy access in the form when collecting data. Remove redundant navigation, staging banners and marketing copy from the calculator; the staging environment remains protected by noindex/security headers.

Validate the visual hierarchy at real mobile widths 320/375/390, including the action button's size and its distance from the result. Successful technical tests alone do not establish that an important action is noticeable. Hold production promotion for owner visual approval.

## Next implementation slices, in order

1. **P0 — finish hosted authenticated E2E.** Reuse Acorde Lab's existing transactional PostgreSQL branch, not a second backend. Reconcile with its fail-closed review branch before merging. Deploy to segregated test credentials and run real hosted two-tenant Chromium E2E; retain redacted SQL receipts and screenshots. Fail release on unsigned/unauthorized writes, missing evidence, repeated provider receipts, or cross-tenant access. **Requires safe staging authorization; do not ask owner to paste tokens in chat.**
2. **P0 — pick one source/connector contract.** Document system of record and two identity-ambiguous fixtures; test read-only import/diff, validation, cancellation, recovery, and operator decisions; then explicitly authorize sandbox writes. Keep unavailable integrations marked *not connected*.
3. **P0 — retain all demo regression gates.** Run mathematical unit + browser + live HTTPS/headers + Tally prefill checks for every staging change; verify deployed revision and visual states across viewports before sharing preview. Do not promote a changed preview if checks fail.
4. **P0/P1 — approve truthful commercial copy and retention.** Public quick estimator must show non-automation and existing-tool baselines, workload values and assumptions, and a prominent disclosure that time value does not establish savings or a quoted product fee. Pricing, legal controller/retention, supplier terms and paid audit deliverables require owner signoff.
5. **P1 — customer-proof pilot.** Secure 3–5 willing teams; validate invoice, staff review/correction hours, failure attribution, implementation and service costs, with a matched before/after window. Report net operating impact and uncertainty separately from hypothetical revenue recovery. Treat negative or negligible economics as valid outcomes.
6. **P1 — release only after green evidence.** Freeze tested commit, verify latest hosted URL against exact deployed revision, monitor real error and payment/lead delivery, document rollback and a stop condition. Do not run public outreach on the staging link.

## Definition of done

**No claim without a test or witnessed integration.** Passing static sample UX and PostgreSQL test fixtures supports only their scope; it does not establish customer production SaaS readiness, CRM connectivity, GDPR certification, real market prices, or actual recoverable revenue.
